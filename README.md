# ZonEaseTech build workflows

Build and verify private release candidates for the ZonEaseTech skills, Shiftly, GotThat (`got-that`), TTPOS CLI (`ttpos-cli`) and TTPOS Lite (`ttpos-lite`) projects. TTPOS CLI is built from the `ttpos-cli/` directory of `ttpos-server-go` at a commit on its `release` branch; only that directory is checked out (partial clone with sparse checkout) and its draft Release goes to `ttpos-server-go`. TTPOS Lite is built from main of `ttpos-lite` and delivers only a verification receipt, `ttpos-lite-checks.zip`, recording that its release-tool, schema and Android candidate checks passed; its signed Android release bundle, `android-release.zip`, is built by `app.yml` (`ttpos-lite`, `android`, `prod`) with the `TTPOS_LITE_*` signing material from the `private-build` environment. GotThat signed Android and iOS packages are built by `app.yml` on public Ubuntu and macOS runners with signing material from the main-only `private-build` environment. GotThat sources are exported as a tarball of an approved main commit at or after `scripts/got-that-minimum-sha`, so older history never reaches the runner. An authorized maintainer can run **Build private release candidates** on main, select the project, and optionally select an exact commit reachable from its main branch. Each project also provides a private dispatch entry point.

The selected revision supplies its build recipe in `scripts/ci-build.sh`. Builds use an isolated Node.js container. Credentials stay on the runner outside that container. Each attempt writes its outputs, diagnostic log, source revision and checksums to a draft Release in the source repository, then downloads and verifies the files. Failed builds deliver diagnostics only. The diagnostic test exercises this failure path.

Only trusted release maintainers should have write access to this repository. The main-only private-build environment issues short-lived GitHub App installation tokens restricted to the selected repository.

For pre-merge checks, use the organization's build-factory skill from the private project. The maintainer verifies that the PR is open, targets main, and comes from a trusted branch of the same repository. Review the exact revision before dispatching. The skill sends its PR number and full head SHA to this public runner. The runner fetches the matching pull ref and checks that its SHA is also a branch tip in the selected private repository. The build container can access the network, so maintainer review of the code and its build recipe is required.

PR runs validate project outputs and write a verification-only private draft tagged `pr-check-<pr>-<run>-<attempt>` with the log, build info and checksums. Compare the still-open PR and exact head again before merging. Run the main build on the merged commit for consumable release candidates. The build App keeps its existing repository contents permissions.
